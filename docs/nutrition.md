# 饮食记录与 AI 饮食计划

本次扩展覆盖 H5 和微信小程序，入口为「饮食记录」。数据按登录用户隔离，业务日期采用 Asia/Shanghai。饮食档案独立保存，首次填写时可参考现有健康档案中的年龄、身高和体重。

## 使用流程

1. 填写年龄、身高、体重、公式使用的性别、目标、日常活动水平、过敏食物和口味偏好，保存饮食档案。
2. 点击添加记录，选择早餐、午餐、晚餐或加餐。可以手动录入食物，也可以从相册选择或拍摄照片。
3. 勾选本次图片发送授权后调用 DeepSeek。识别结果包含食物、估计份量、碳水化合物、蛋白质和脂肪；保存前可以修改。识别完成本身不会自动写入饮食记录。
4. 保存后查看当日摄入、三大营养素、运动消耗和记录口径热量差。可修改或删除记录，统计随之重新计算。
5. 在饮食计划中选择简单易执行、均衡进阶或精细管理，生成七日、每日三餐的草稿。查看后确认启用，逐餐打卡会生成对应的实际饮食记录；未到日期不能提前计入摄入。

拍照入口依赖设备能力与权限；桌面浏览器通常主要使用相册文件选择。取消选择不会发起识别。图片不得超过 4 MiB，接受 JPEG、PNG、WebP，服务端还会检查文件头。H5 本地图片使用数据 URL，微信端通过文件系统读取；照片不需要公开访问地址。

## 计算口径

基础代谢采用 Mifflin–St Jeor 的静息能量估算式，需要身高。男性为 `10×体重kg + 6.25×身高cm − 5×年龄 + 5`，女性末项为 `−161`。此值是公式估算，并非间接测热测量结果。依据：[原始论文摘要](https://pubmed.ncbi.nlm.nih.gov/2305711/?dopt=Abstract)。

食物能量统一按 `4×碳水g + 4×蛋白质g + 9×脂肪g` 计算，避免模型报告的热量与营养素相互矛盾。这是三大营养素口径；纤维、糖醇、酒精、包装标签的舍入差等没有独立建模。

运动仅使用已经完成的运动打卡，不把未完成的计划计入消耗。按活动类型采用代表性 MET 参数：跑步 8、力量 3.5、瑜伽 2.5、步行 3.5、骑行 6，计算超过静息部分的净消耗：`(MET−1)×3.5×体重kg÷200×分钟`，减少与基础代谢重复计算。活动强度因人而异，这不是运动设备测量值；参数是产品估算，参考 [Physical Activities Compendium](https://pacompendium.com/) 的 MET 方法，不能视为每一次运动的精确值。

页面的记录口径热量差为 `基础代谢 + 净运动消耗 − 已记录饮食摄入`。正值表示该口径下的缺口，负值表示盈余。它没有完整包含日常非运动活动和食物热效应，因此不等于完整 TDEE 赤字。当天尚未记录饮食时显示未记录，不将零记录当作实际禁食或计算出的赤字；一天只记录一餐时也仅代表已记录部分。

每个有档案的日期在首次保存餐食时保留基础代谢、体重、目标热量与档案版本。以后修改档案不会重算旧快照。未建快照的日期使用当前档案作估算并返回依据标识，缺少档案时不计算热量差。

图表支持当天按餐次、自然周（周一至周日）按天、自然月按天的摄入统计。没有记录的日期保留空状态；图表的零柱表示没有记录，不能推断实际没有进食。

## 计划生成规则

服务端使用基础代谢乘日常活动系数（久坐 1.2、轻度 1.375、中度 1.55）估算计划目标，减脂减 300 kcal、维持不调整、增肌加 200 kcal，设置女性 1200 / 男性 1500 kcal 的产品下限。这是通用目标规则，不代表每个人都适用的营养处方。三种风格改变备餐复杂度、食材变化和称重精度，使用相同热量边界，不通过扩大缺口体现「进阶」。

草稿需要通过七个连续日期、三餐唯一性、营养值范围、份量一致性、每日热量边界、蛋白质和脂肪比例检查。模型第一次输出不合格时可进行一次纠正，共用截止时间；最终仍不合格则提示失败，不启用计划。已声明的常见过敏原进行同义词检查，但复杂配料和交叉接触无法靠模型完全排除，页面要求复核。

自动计划面向成年人；有妊娠、哺乳、进食障碍、需医疗营养管理等情况时应选中需要专业评估，暂停自动规划。手动记录可以继续使用。参考 [NIDDK 热量计划说明](https://www.niddk.nih.gov/health-information/diabetes/overview/preventing-type-2-diabetes/game-plan)。

## 模型、配额与隐私

沿用后端 `DEEPSEEK_API_KEY`。图片模型默认 `DEEPSEEK_VISION_MODEL=deepseek-flash`，饮食计划可使用 `DEEPSEEK_DIET_MODEL`，未设置时沿用训练教练模型。图片使用标准 Chat Completions 的 `image_url` 数据块，依据 [DeepSeek 官方图片输入文档](https://api-docs.deepseek.com/guides/vision/)。实际可用性以本地账号、所配模型和上游返回为准。2026-10-22 真实隔离测试已通过：合法线条图触发无食物拒绝，七日饮食计划通过校验、启用并完成一餐打卡；这不代表已验证真实餐食识别准确率。见 [联调记录](deepseek-nutrition-verification.json)。

图片识别和饮食计划共用独立的每用户 12 次／过去 60 分钟限制；已受理失败也计次，内部纠正不额外计次。页面显示剩余次数，DeepSeek 限流、余额不足、服务繁忙与本系统配额分别提示。每用户一次活动任务，当前进程最多四次；生成通过后台任务查询进度，刷新页面不会重复发起付费请求。

图片只在明确授权后发送给 DeepSeek；计划仅发送饮食档案、偏好和计划参数。密钥保留在后端，不发送登录令牌、昵称或数据库连接。照片作为私有记录存储，照片接口必须验证所有者；其他用户不能借图片 ID 访问。关闭未保存的识别会清理照片，删除最后一条关联餐食也会在同一事务中擦除照片和识别内容；只保留用于计次的最小任务记录。照片与饮食资料没有应用层加密，不能将本地开发配置直接视为生产存储方案。

任务执行在当前 API 进程，重启不会自动重放模型请求，残留活动任务查询时标记中断。多实例部署仍需要共享队列、容量控制和对象存储。本次默认用数据库私有图片字段，备份和容量规划应包括图片；大规模部署建议迁移至私有对象存储。

## 文件与验证

- `database/006_nutrition.sql`：档案、任务、每日依据和餐食四张表，外键、幂等键、单活动任务与单启用计划约束。
- `apps/api/src/nutrition/`：领域公式、模型适配、接口、校验和响应合同。
- `apps/web/src/components/NutritionTracker.vue`：响应式中英文页面。
- `docs/diagrams/nutrition-er.mmd`、`nutrition-architecture.mmd`：可维护图源。
- `tests/nutrition*.test.ts`：领域、接口与隔离验证。
- `npm run test:nutrition`：真实前后端路由、独立内存数据库、明确的模型 Mock，避免使用真实用户资料或产生模型费用。

真实模型隔离联调可运行 `npx tsx scripts/verify-deepseek-nutrition.mts`，使用虚构成年人档案与测试线条图，会产生模型费用，不纳入 CI。`--diagnostic` 仅将模型返回写入忽略的 `.data/`，不保存请求头和密钥。测试线条图仅验证图片协议及无食物拒绝，不能代替真实餐食识别精度验收。

运行 `npm run dev:api` 会执行可重入迁移；重启后端、刷新 H5，或重新构建并导入微信小程序。正式微信拍照、相册授权和真机请求域名仍需在实际 AppID 环境验证。
